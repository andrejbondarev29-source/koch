# BRANCH_CONTEXT.md — ветка `testing`

> Контекстный файл для AI-агентов и нейросетей. Дополняет корневой `AGENTS.md` и
> действует **только в ветке `testing`**. При конфликте правил действует более строгое;
> прямое явное указание пользователя важнее любого пункта ниже.

## 1. Роль ветки

`testing` — рабочая ветка для тестирования кода DvorFight: прогона автотестов,
воспроизведения и проверки багов, регрессионных прогонов перед релизом. Это не релизная
ветка и не песочница для экспериментов: её единственная задача — **найти дефекты до того,
как код попадёт в `staging` или `main`**, и подтвердить, что исправления действительно
работают.

Ветка не является источником игровых изменений. Код здесь проверяется, а не развивается.

## 2. Типовые задачи этой ветки

- Прогон обязательной сборки: `dotnet build DvorFight.csproj -c Release` (0 ошибок,
  0 предупреждений).
- Headless-самотест: `run.cmd --selftest`, ожидается `RESULT: PASS` и код возврата 0.
- Расширение и починка проверок в `Diagnostics/SelfTest.cs`, если найден непокрытый
  сценарий (меню, сложности бота, каталог бойцов, баланс).
- Воспроизведение багов по шагам и фиксация фактического поведения.
- UI-проверка скриншотами через `--screenshot` и личный просмотр PNG (шрифты,
  выравнивание, отсутствие наездов и обрезки в холсте 960×480).
- Регрессионные прогоны после слияния свежего `main`.
- Подготовка короткого отчёта: что проверено, чем, результат, найденные дефекты.

## 3. Что здесь разрешено

- Добавлять и править **только проверки** в `Diagnostics/SelfTest.cs` и вспомогательные
  тестовые утилиты, если они не меняют поведение игры.
- Добавлять тестовые данные и фикстуры, не влияющие на релизную сборку.
- Править документацию **по тестированию** (раздел README о самотесте, локальные
  заметки о прогонах), не трогая остальные разделы без необходимости.
- Вносить минимальные исправления кода, без которых проверка невозможна или падает:
  отдельным коммитом `fix(...)`, с явным описанием причины в сообщении и в отчёте.
  Такие правки должны быть переносимы в `main` без конфликтов.
- Перегенерировать скриншоты, если прогон выявил регрессию вёрстки, — но **не
  «улучшать» интерфейс** и не менять дизайн.
- Удалять временные файлы прогонов (логи, кропы, `_zoom_*.png`) до коммита.

## 4. Что строго запрещено

- Менять игровые числа в `Config/Balance.cs` и `AI/BotDifficultyProfile.cs` ради
  «зелёного» теста.
- Менять геймплей, физику, AI, правила боя, порядок экранов и вёрстку «по ходу» тестов.
- Ослаблять или удалять существующие утверждения самотеста без доказанной причины;
  подгонять тест под баг вместо фиксации бага.
- Рефакторить, переименовывать и удалять существующие файлы проекта.
- Менять `AGENTS.md` и `.clinerules` — это делается в `main` отдельной задачей.
- Коммитить `bin/`, `obj/`, `.vs/`, логи, временные кропы, секреты и абсолютные
  пользовательские пути.
- Делать `git push` в `main`, `force-push`, переписывать опубликованную историю.
- Добавлять тяжёлые ассеты — для них есть ветка `assets-storage`.
- Смешивать несколько несвязанных проверок в одном коммите.

## 5. Обязательный порядок работы

1. `git fetch origin`; ветка создаётся/обновляется от актуальной `main`:
   `git checkout -b testing main` или `git merge main` в существующей ветке.
2. Убедиться, что рабочее дерево чистое; чужие незавершённые изменения не смешивать
   со своей задачей.
3. Собрать: `dotnet build DvorFight.csproj -c Release` — 0 ошибок, 0 предупреждений.
4. Прогнать `run.cmd --selftest` — `RESULT: PASS`, код возврата 0.
5. При изменениях UI снять PNG dev-флагами и **лично прочитать изображения**.
6. Проверить `git diff --check` и `git status` — в индексе только осмысленные изменения.
7. Коммит в стиле `test(scope): ...` или `fix(scope): ...` (императив, по-русски).
8. `git push -u origin testing`.

## 6. Definition of Done для этой ветки

- [ ] Сборка Release: 0 ошибок, 0 предупреждений.
- [ ] `run.cmd --selftest`: `RESULT: PASS`.
- [ ] Для UI-проверок PNG сняты и просмотрены глазами.
- [ ] Найденные дефекты описаны воспроизводимо (шаги, ожидание, факт, окружение).
- [ ] В коммите нет артефактов сборки, временных файлов и секретов.
- [ ] Ветка запушена в `origin`; `main` не изменён.

## 7. Связь с другими ветками

- `main` — эталон и источник истины; сюда возвращаются только проверенные исправления
  через PR.
- `staging` — предрелизная проверка; код попадает туда только после зелёного прогона
  в `testing`.
- `assets-storage` — склад тяжёлых ассетов; тестовые медиафайлы здесь не хранятся.

Если задача требует изменить геймплей, баланс или интерфейс — это не задача ветки
`testing`: остановиться и согласовать работу в отдельной ветке от `main`.
