# BRANCH_CONTEXT.md — ветка `staging`

> Контекстный файл для AI-агентов и нейросетей. Дополняет корневой `AGENTS.md` и
> действует **только в ветке `staging`**. При конфликте правил действует более строгое;
> прямое явное указание пользователя важнее любого пункта ниже.

## 1. Роль ветки

`staging` — предрелизная ветка-песочница DvorFight, максимально приближенная к
продакшену. Здесь код проходит **финальную проверку перед выкаткой**: сборка в
Release-конфигурации, самотест, визуальная проверка экранов и прогон по релизному
чек-листу. Всё, что находится в `staging`, должно быть готово к выпуску без доработок.

`staging` — не место для разработки. Ветка должна быть стабильной в любой момент времени:
в ней не бывает «временных» коммитов, незакоммиченных экспериментов и выключенных проверок.

## 2. Типовые задачи этой ветки

- Приём кода, уже прошедшего проверку в `testing` (слияние или аккуратный cherry-pick).
- Сборка релизного кандидата и подтверждение: 0 ошибок, 0 предупреждений.
- Прогон `run.cmd --selftest` — `RESULT: PASS`, код возврата 0.
- Смоук-прогон всех экранов (`--screen title|fighters|fight`) и личный просмотр PNG.
- Проверка релизных метаданных: версия, название, описание, README, заметки о выпуске.
- Подготовка релизного чек-листа и отчёта: что входит в выпуск, что проверено, риски.
- Финальные мелкие правки, без которых выпуск невозможен (release hotfix), — только с
  явного согласования и отдельным коммитом.

## 3. Что здесь разрешено

- Сливать в `staging` только ветки/коммиты, которые уже прошли полный зелёный прогон
  в `testing` (сборка + самотест + скриншоты, если менялся UI).
- Обновлять релизные метаданные и документацию выпуска (`README.md`, release notes),
  не меняя смысл опубликованных правил.
- Править релизную конфигурацию сборки, если это требуется для выпуска и согласовано.
- Вносить минимальные hotfix-правки, блокирующие выпуск: отдельный коммит `fix(...)`,
  с описанием риска и обязательным последующим переносом в `main`.
- Перегенерировать релизные скриншоты, если они устарели относительно проверенного UI.
- Удалять временные файлы прогонов до коммита.

## 4. Что строго запрещено

- Вести разработку новых функций, экспериментировать, рефакторить «по пути».
- Менять игровые числа (`Config/Balance.cs`, `AI/BotDifficultyProfile.cs`), геймплей,
  физику, AI или вёрстку без отдельной задачи и согласования.
- Ослаблять самотест, отключать проверки или подгонять их под текущее поведение.
- Вливать код, не прошедший `testing`, или «временно» ломающий сборку/самотест.
- Коммитить `bin/`, `obj/`, `.vs/`, логи, временные кропы, секреты, токены, ключи.
- Хранить в этой ветке тяжёлые медиаассеты — для них есть `assets-storage`.
- Делать `git push` в `main`, `force-push`, переписывать опубликованную историю.
- Ставить релизные теги и публиковать релиз без явного указания пользователя.
- Смешивать подготовку релиза с посторонними изменениями в одном коммите.

## 5. Обязательный порядок работы

1. `git fetch origin`; ветка создаётся/обновляется от актуальной `main`:
   `git checkout -b staging main` или `git merge main`.
2. Убедиться, что принимаемые изменения уже зелёные в `testing`; иначе — вернуть
   их на доработку, а не «дожимать» здесь.
3. Собрать: `dotnet build DvorFight.csproj -c Release` — 0 ошибок, 0 предупреждений.
4. Прогнать `run.cmd --selftest` — `RESULT: PASS`, код возврата 0.
5. Снять и лично просмотреть PNG всех затронутых экранов (960×480, без наездов и обрезки).
6. Проверить `git diff --check`, `git status` и итоговый diff — только осмысленные
   релизные изменения.
7. Коммит в стиле `release(scope): ...` или `fix(scope): ...` (императив, по-русски).
8. `git push -u origin staging`.

## 6. Definition of Done для этой ветки

- [ ] В `staging` нет кода, не прошедшего `testing`.
- [ ] Сборка Release: 0 ошибок, 0 предупреждений.
- [ ] `run.cmd --selftest`: `RESULT: PASS`.
- [ ] Релизные экраны проверены по PNG глазами.
- [ ] README и заметки о выпуске соответствуют фактическому состоянию.
- [ ] Ветка запушена в `origin`; `main` не изменён; теги не ставились без разрешения.

## 7. Связь с другими ветками

- `main` — эталон и источник истины; `staging` отвечает только за подготовку выпуска.
- `testing` — обязательный фильтр: сюда попадает только то, что там уже зелёное.
- `assets-storage` — склад тяжёлых ассетов; в `staging` хранится только код и документация.

Если для выпуска требуется изменение геймплея, баланса или интерфейса — остановиться,
согласовать задачу и провести её через отдельную ветку от `main`, затем через `testing`.
